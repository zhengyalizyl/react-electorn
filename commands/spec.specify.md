把需求拆成规格。这是整条链路的第一环，产出 `spec.md` 的第一、二层。

先读 `spec-workflow` skill，重点是「写规格的硬规则」与「产物落位」两节。

原始需求：$ARGUMENTS

## 步骤

1. **定位项目根**：当前工作目录所在的项目（有 `AGENTS.md` 与 `package.json` 的那一层）。

2. **分配编号**：读 `specs/` 下已有目录，取最大序号 +1，三位零填充。
   起一个简短英文 kebab-case slug，准确描述这个需求做什么。

3. **确认建分支**：AGENTS.md 禁止未经确认的 Git 操作，所以必须先问用户：

   ```
   即将创建分支 NNN-slug 并切换过去，同时创建 specs/NNN-slug/。
   请确认是否继续？
   ```

   用户拒绝就只建目录，不建分支，并在 `spec.md` 的分支栏写「未启用」。

4. **写 spec.md**：读 `spec-workflow/templates/spec-template.md`，按模板填。

5. **先读代码再动笔**。需求大概率与既有实现有关系：
   - 用 Grep/Glob 找相关的既有页面、组件、主进程能力
   - 在「背景」里写清当前是什么状况
   - 在「边界约束」里写清哪些既有行为不能破坏

## 质量自检

写完逐条核对，不过关就改：

- [ ] 全文没有框架名、库名、文件路径（那些属于 `plan.md`）
- [ ] 每个用户故事都能独立交付——P1 单独做完能上线并产生价值
- [ ] 每条验收标准都是 Given/When/Then，且可判定
- [ ] 成功指标可量化且与技术无关
- [ ] 边界情况与异常处理不为空（只写 Happy Path 是最常见的失败）
- [ ] 每条 FR 编号唯一，且都能追到某个用户故事
- [ ] 拿不准的地方都标了 `[NEEDS CLARIFICATION: ...]`，没有一处是猜的

## 结束时

汇报：编号与分支、用户故事数量与优先级分布、FR 条数、待澄清条数。

有待澄清项就提示用户跑 `/spec.clarify`；没有则提示：
有界面跑 `/spec.design`，无界面直接 `/spec.plan`。
