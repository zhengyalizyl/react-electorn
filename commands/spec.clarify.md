消解规格里的待澄清项。**不猜默认值**——这是 Spec Driven 链路上最贵的错误。

先读 `spec-workflow` skill 的「写规格的硬规则」。

目标需求：$ARGUMENTS（留空则取 `specs/` 下序号最大的）

## 步骤

1. 读 `specs/NNN-slug/spec.md`，提取全部 `[NEEDS CLARIFICATION: ...]`。
   一条都没有就直接汇报「无待澄清项」并结束，不要为了跑而跑。

2. **先自己查**。有些问题不用麻烦用户，从项目里能确认：
   - 既有代码、配置、`AGENTS.md`、skill 文档能回答的，自己查，把结论直接写回
   - 查到的结论要在汇报里说明依据（哪个文件、哪一行）

3. **剩下的才问用户**。用 AskUserQuestion 一次问完，每个问题：
   - 给 2–4 个具体选项，不要开放式提问
   - 推荐项放第一个并标注「（推荐）」
   - 说清每个选项的**后果**，不是复述选项本身

4. **写回**：把结论写进 `spec.md` 对应章节（背景 / 用户故事 / FR / 边界情况 / 假设），
   删掉该条 `[NEEDS CLARIFICATION]`。

   结论如果引入了新的 FR 或验收标准，一并补进去并编号。

5. **连带检查**：澄清后是否与既有 FR 冲突、是否让某个用户故事不再独立可交付。
   有就一并调整。

## 结束时

汇报：消解了几条、其中几条是查代码确认的、几条是用户决断的、新增了哪些 FR。
仍有未决项时说明为什么（例如依赖外部方还没答复），不要假装已解决。

全部收口后提示：有界面跑 `/spec.design`，无界面直接 `/spec.plan`。
