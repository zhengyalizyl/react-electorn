开工前的最后一道门禁。**只读，不修改任何文件**，输出问题清单由用户决断。

目标需求：$ARGUMENTS（留空则取 `specs/` 下序号最大的）

读齐 `spec.md`、`design.md`（若有）、`plan.md`、`tasks.md`、`AGENTS.md`。

## 检查项

### 覆盖
- [ ] `spec.md` 的每条 FR 在 `tasks.md` 里都有任务
- [ ] 每条验收标准都有对应的验证手段
- [ ] 每个 P 级用户故事在 `tasks.md` 里都有独立的一组任务
- [ ] 有界面的需求，`design.md` 的每个 frame 都有实现任务

### 反向覆盖（更容易被忽略）
- [ ] `tasks.md` 里没有追不到任何 FR 的任务——追不到就是范围蔓延
- [ ] `plan.md` 里没有规格没要求的设计
- [ ] `design.md` 里没有规格之外的界面

### 一致性
- [ ] `plan.md` 的目录结构与 `tasks.md` 的文件路径对得上
- [ ] `design.md` 的 frame id 与 `tasks.md` 引用的一致
- [ ] 三份文件对同一概念用同一个名字（同一个东西不要一处叫"分镜"一处叫"片段"）
- [ ] `design.md` 的令牌与 `plan.md` 的样式方案对得上

### 分层
- [ ] `spec.md` 里没有技术细节（框架名、库名、文件路径）
- [ ] `plan.md` 里没有偷偷改需求
- [ ] 没有残留的 `[NEEDS CLARIFICATION]`

### 宪法
- [ ] `plan.md` 的门禁表逐条有结论
- [ ] 豁免项都写了理由与备选方案
- [ ] `tasks.md` 没有引入绕过 lint / typecheck / 测试的任务

### 可执行性
- [ ] 每个任务的完成标准可判定
- [ ] `[P]` 标注没有同文件冲突
- [ ] 连带改动（dedupe、别名两处、IPC 四处、路由表、`@theme`）都有显式任务

## 输出

按严重度分组，每条写：**问题 / 位置 / 影响 / 建议**。

- **阻断**：不改就不能开工（FR 无任务覆盖、门禁未结论、残留待澄清）
- **风险**：能开工但大概率返工（命名不一致、连带改动缺任务）
- **建议**：可选优化

全部通过就明确说「无阻断项，可以开工」，不要为了显得有用而凑问题。

不修改文件。不执行 Git 操作。
