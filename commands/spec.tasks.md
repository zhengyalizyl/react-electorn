任务规划。把方案拆成能一条条执行、一条条验收的任务。

先读 `spec-workflow` skill 的「产物落位」一节。

目标需求：$ARGUMENTS（留空则取 `specs/` 下序号最大的）

## 前置检查

`plan.md` 存在，且宪法门禁全部有结论。门禁没过就先回 `/spec.plan`。

## 步骤

1. 读 `spec.md`（要 FR 与验收标准）、`plan.md`（要目录结构与决策）、
   `design.md`（有界面时，要 frame id）。

2. 读 `spec-workflow/templates/tasks-template.md`，按模板拆。

3. **按用户故事分组**，不是按技术层次分组。
   一组做完就应当是可交付、可验证的完整切片——
   「先把所有主进程写完，再写所有页面」是错的拆法，那样任何一组做完都验证不了。

4. **每个任务必须写清**：
   - 改哪些文件（具体路径，不是「相关组件」）
   - 怎么算完成（可判定，不是「实现好」）
   - 对应哪条 FR

5. **标注 `[P]`**：不同文件、互不依赖的任务可并行。同一文件的任务绝不标 `[P]`。

6. **连带改动要拆成显式任务**，这类最容易漏：
   - 新 React 库 → `vite.renderer.config.ts` 的 dedupe + optimizeDeps
   - 新路径别名 → `vite.renderer.config.ts` + `tsconfig.json` 两处
   - 新 IPC → handler + preload + 全局类型 + eslint globals 四处
   - 新页面 → 页面文件 + 路由表
   - 设计稿新令牌 → `renderer/index.css` 的 `@theme`

7. **填覆盖核对表**。每条 FR 都要有任务覆盖，每条验收标准都要有验证手段。
   这张表是暴露缺口用的，发现缺口就补任务，不要填个「已覆盖」糊弄过去。

## 质量自检

- [ ] 每个故事组单独做完都能交付
- [ ] 每个任务都写了文件路径与完成标准
- [ ] `[P]` 标注没有同文件冲突
- [ ] 连带改动都有显式任务
- [ ] 覆盖核对表没有空行
- [ ] 收尾阶段包含 `/spec.uicheck`（有界面）与 `/spec.verify`

## 结束时

汇报：任务总数、按故事的分布、可并行任务数、覆盖核对是否有缺口。
提示下一步：想先做一致性检查跑 `/spec.analyze`，直接开工跑 `/spec.implement`。
